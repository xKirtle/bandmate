# Timeline placement rules are checked once, on what a change leaves

The Timeline's placement rules are checked once, on the Timeline a change leaves, never a Clip at a time partway through the change. The rules are: a Clip starts on the Timeline; no two Clips on a Track overlap; a Clip stays within its source; and its Fades fit it. Operations write their Clips without checking where they land. Every change runs through one path, which reads the Timeline before and after and hands both to one pure check, `checkLayout`. The check looks only at the Clips the change made or altered, so a Song whose stored layout is already slightly off never refuses the edit that would fix it. It returns which rule broke on which Clip, not a message, so an operation can put a refusal in its own words, as nudging a Take does with "trim it first".

Checking each Clip as it was written made the order of writing matter. Moving several Clips had to store them all before checking any. Setting several Tempos had to go latest-first and pass along the Clips leaving. Getting that order wrong caused bugs, and the rules could only be tested by driving the whole HTTP server. Checking the result instead makes order irrelevant, and the rules are table-tested on plain Timeline values. The cost is reading the Timeline once more per change. The database still refuses a Clip that starts before 0:00 or before its source, or that plays for no time, so those three are refused as each Clip is written, in the rule's own words. That looks only at the Clip being written, never at other Clips, so order still doesn't matter. No operation should add per-Clip placement checks back. The searches for where a Clip fits (adding a Beat, a Duplicate, a slowed Clip's new Track) still query the database: they find a place rather than refuse one.
