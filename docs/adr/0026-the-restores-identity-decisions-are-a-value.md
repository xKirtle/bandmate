# The Restore's identity decisions are a value, and the bulk fresh ids stay in SQL

A Restore decides which id each row it brings back gets. For the four tables carrying identity rules — Folders and Tags matched by their folded names (0015), Songs and Beats matched by their Identity and replaced or kept both — that decision is now a value: a pure function takes what the Backup holds, what's already in Bandmate, the Picks and what's being replaced, and returns, per row, the id it gets and what that id means (matched, and under which name; replaced, and the version it follows; kept both). The copy then writes those decisions with one parameterised insert per table and carries on as before, reading them back out of the same temporary table it always has. The ids handed out are the ones the generated SQL handed out, row for row: restored ids show in API replies, and a Backup's fingerprint hashes rows.

The decisions are the subtlest logic in the backend, and they were expressed as SQL built with `fmt.Sprintf`, three passes writing into a temporary table, verified only by driving the HTTP server against SQLite in a temporary directory. They're table-tested on plain Go values now — a Tag that exists in another case, a Song from another install that must never count as already there, the same Beat arriving from two picked Songs, a name match whose row went with the Song being replaced — as the Lyric Sheet's rules (0024) and the Timeline's placement (0025) are, and the HTTP tests are the safety net that proves the path end to end.

The ids of the other 13 tables a Song's rows live in stay worked out in SQL, where the rows are. Those tables hold no decision to get wrong: each row gets a fresh id in Backup-id order and nothing else. They also hold by far the most rows, so reading them into Go to hand each an id and write it straight back would buy nothing but round trips. **Planning all 17 tables in Go was the rejected alternative**: it would make the plan the one place ids are decided, at the cost of carrying every Line, Clip and Take of every Song picked through Go for a number SQLite can count out itself, and it would hide the thing worth seeing — that only four tables decide anything. This split is deliberate, and the code says so where it branches: a new table holding identity rules joins the plan, one holding none keeps its fresh ids in SQL.

0013 is untouched: a Backup is still a small Bandmate database, brought up to this schema in a staging directory, and nothing here changes when its migrations run. `Present`, which answers "already in Bandmate?" for the list the user picks from, still asks the live database row by row rather than through the plan; folding the two together would change a user-facing list, so it's grilled on its own.
